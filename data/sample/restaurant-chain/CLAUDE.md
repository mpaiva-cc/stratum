# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

This folder is **both an Obsidian vault and the output of one Python generator**. It is a worked sample of the Stratum *contextual map* (the substrate formerly called the "people graph"): "Fork & Flame", a fictional 20-store / 500-employee casual-dining chain, modeled as the full HCM-universe entity set. Every entity is a Markdown note; every relationship is a wiki-link, so Obsidian's graph view renders the contextual map directly.

It lives at `data/sample/restaurant-chain/` inside the larger `poc-autonomous-hcm` (Stratum) Jekyll site, but is self-contained — nothing here imports from the parent site.

## The one rule that matters

**`_generate.py` is the single source of truth. Everything else in this folder is generated output.** Each run wipes the entire folder (every file *except* `_generate.py` — including `README.md` and the `.obsidian/` config) and rebuilds from scratch (`_generate.py:301-306`).

So: **never hand-edit a `.md` note, `README.md`, or `.obsidian/*` to make a content change** — it will be destroyed on the next regen. Edit `_generate.py` instead, then regenerate. The only file safe to edit directly is `_generate.py` itself (and this `CLAUDE.md`).

## Regenerate

```bash
python3 data/sample/restaurant-chain/_generate.py
```

Pure stdlib, no dependencies, no network. Deterministic — seeded RNG (`SEED = 20260615`), so the same code always produces the same vault; a diff after regen means the code changed, not noise. There are no tests, build, or lint steps. Verify a change by regenerating and inspecting the output notes / the printed summary counts.

## Architecture of the generator

`_generate.py` runs top-to-bottom as a script (no `main()`), in this order:

1. **Helpers** (`slug`, `link`, `yaml_value`, `note`) — `note(folder, title, frontmatter, body)` is the single writer for every `.md` file. Frontmatter dict → YAML; body is Markdown. `slug()` sanitizes titles into filenames; `link()` wraps a title as `[[wikilink]]`.
2. **`ENTITY_CATALOG`** (`_generate.py:83`) — the master list of all ~24 HCM entity types as tuples `(type, group, basis, oneline, properties, edges)`. This is the schema. **To add or change an entity type, edit this list.** `emit_schema()` renders one `_schema/type-*.md` note per entry.
3. **Data pools** (`FIRST`, `LAST`, `REGIONS`, `CITIES`, `POSITIONS`, `SKILLS`, `CERTS`, ...) — the vocabularies instances are sampled from.
4. **Instance emission** — sequential blocks build the org → regions → departments → positions → stores → people → shifts/schedules → sampled long tail (time-off, reviews, devices, candidates, tip pools, benefits, policies, consent grants, training, onboarding, events). Cross-entity maps like `CERT_FOR_POS`, `SKILL_FOR_DEPT`, `PAY_FOR_POS` keep instances internally consistent.
5. **README + `.obsidian/` config** are written last (graph color-groups keyed by folder path), then a summary is printed.

## Two layers, mirrored

- **`_schema/`** — one note per *entity type* (`type-person`, `type-store`, `type-agent`, ...): the documented catalog. Lists each type's properties, its edges to other types, and its governance basis. Generated by `emit_schema()` from `ENTITY_CATALOG`.
- **Instance folders** (`People`, `Stores`, `Shifts`, `Schedules`, `Events`, `Governance`, ...) — the actual data. The `type:` frontmatter field on an instance note matches a `_schema/type-*` entry.

When you change an entity type's properties or edges, change it in **both** places: the `ENTITY_CATALOG` tuple (schema) and the instance-emission block that writes those notes (instances). They are not auto-synced.

## Conventions every note follows

- **Properties = YAML frontmatter; relationships = wiki-links** (in frontmatter values and/or body). Edges are quoted `"[[Target]]"` strings.
- **IDs** are typed prefixes: `EMP-` people, `ORG-`/`REG-`/`DEP-`/`POS-` org entities, `CND-` candidates, etc. (`nid(prefix)` mints sequential ones).
- **Filenames** generally embed the ID + display name, e.g. `EMP-0001 Mateo Thomas.md`, `Store 01 - Austin Domain.md`.
- **Governance basis** (the v6 governance-basis model) is carried as `basis:` on *every* note:
  - `consent` — data subjects (`person`, `candidate`, `pay_rate`, certifications, consent grants...).
  - `authorization` — institutional entities that don't consent (`store`, `location`, `position`, `department`, `device`, `policy`...).
  - `delegated_authority` — `agent`, which operates under authority the company extends (lifetime = its policy version, not a tenure).
  This is what makes the contextual map governance-aware end to end; preserve it when adding entity types.

## HCM system of understanding (the query app)

`index.html` + `app.js` + `ff-engine.js` turn this vault into a governance-enforced
query layer. Open `index.html` directly (it runs off `file://`; BYO Anthropic key,
kept in-browser). Plain-language question → `ff-engine` traversal spec (via Claude
tool use) → deterministic engine that **enforces consent in code** → narrated answer
with the query, a governance trace, and citations.

- `ff-engine.js` — pure, dual-mode (Node + browser) engine. **Governance lives here,
  not in the LLM.** Tested: `node --test data/sample/restaurant-chain/*.test.js`.
- `forkandflame.graph.json` / `.graph.js` — the served fixture. **Generated** by
  `_generate.py` (`emit_fixture()`); never hand-edit.
- Consent grants (`Governance/*consent*`) are also generated — comprehensive and
  purpose-aligned, with a deliberate minority declined/expired/revoked so refusals
  fire. Change the generator, not the notes.
- The wipe step whitelists `index.html`, `app.js`, `ff-engine.js`, `ff-engine.test.js`,
  `ff-starters.test.js`, `CLAUDE.md`; everything else (notes, fixture) is rebuilt each run.

Governance: purposes `scheduling|payroll|compliance|employment` map 1:1 to scopes
`hr.scheduling|hr.payroll|hr.certifications|hr.employment`. Default-deny: a gated
field/edge is readable only under its matching purpose AND with an active, unexpired
grant; refusal reasons are `out-of-purpose|no-grant|revoked|expired`. Note: `pay_rate`
mixes units (salaried `year` vs hourly), so cross-position pay averages are not
meaningful — query within a single position (e.g. Server).

### Role-based permission layer

A second access axis beside consent/purpose, enforced in the engine and AND-combined:
- `ff-roles.js` — five viewer personas (CHRO / HRBP / manager / IC / peer): each a
  population rule + allowed scopes. Anchors are concrete fixture people (configurable).
- `ff-engine.js` — `runSpec(spec, db, purpose, role)` (role optional → no role-gate, so
  prior behavior/tests are unchanged). The role-gate is row-level (population, computed
  from `reports_to` / `works_at` / store-region edges) + field-level (allowed scopes).
  `readField` + `nodeReadable` are the canonical enforcement predicates (role authority,
  then consent); the older `canRead*` predicates are consent-only and not on the
  enforcement path. The refusal trace carries a `layer`: `access`
  (`out-of-population`, `role-restricted`) vs `consent`
  (`out-of-purpose|no-grant|revoked|expired`). When both block a field, access wins.
- UI: a "Viewing as" selector + a permission panel showing, per role, who and what is
  visible (live population counts); the governance trace is grouped by layer.
