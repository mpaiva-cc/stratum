§ I — How to read thisThe badge is the contract.

This is the companion to WP-01 § 10. That section is the overview — the envelope, the module map, the four worked examples, and the version history. This document is the exhaustive part: every property of every node and edge, with its type, its required/optional/derived status, and what it means. Pillar authored these tables; Forge ratified each type at its version and owns the status badges.

Status badge — every node, edge & property carries one

canonical vN
In production at schema version vN. Build against it freely.
ratified vX.Y
Ratified as a formal spec of an existing shape, or an additive layer that ships without rewriting an edge. Stable; the version is the minimum graph version that carries it.
proposed vX.Y (not yet shipped)
Not in production today. Intended for the named version; the migration may still change it. Do not build against it as available.
open question
A named known gap. No shape committed.

In the property tables, the req column reads req (required on every write), opt (optional), or derived (computed at projection/query time, not a stored graph property — these appear in the flat demo fixtures but are not part of the schema). The honesty discipline of §8 of WP-01 applies here in the small: a field that is computed is marked computed, never presented as stored.

materialized view person_current canonical v3

Not a node type — a Postgres materialized view that pre-resolves the highest-confidence claim per (person, attribute) pair, rebuilt incrementally on every identity-layer write (~0.6× the storage of the raw edges; ~8× saved on the median read). The flat demo fixture people.json is a projection of this view plus computed fields. Fields that are stored claims: given_name, family_name, display_name, email, title, level, department, team, location, country, region, hire_date, employment_type, gender. Fields that are computed at projection time, not stored: tenure_years, comp_ratio, flight_risk, flight_risk_band, span_of_control, is_manager, performance_score, promotion_eligible.

edges requires · has_skill canonical v3

requisition → skill · requires · extra: weight float req [0,1]; required_level enum opt (novice|intermediate|advanced|expert) · consent: ["recruiter.ats"]
candidate → skill · has_skill · envelope's confidence required (fit-score threshold 0.55); extra: attested_level enum opt · consent: ["recruiter.ats", "recruiter.scoring"]

edge applied_for ratified v3.2

candidate → requisition · extra: applied_at ts req (valid_from on the edge) · consent: ["recruiter.ats"]

Today the link is a denormalized candidate.requisition_id fk. Normalizing it into a first-class bitemporal edge enables tracking the application state and the withdrawal/rejection history over time. This edge is ratified at v3.2 — the Chairman greenlit the migration. Rollout: the edge is dual-written alongside the existing candidate.requisition_id fk; the fk stays authoritative through a dual-read window; then it is deprecated and reads cut over to the edge. Migrate to applied_for; do not write new dependencies on the fk. (Generator emission of the edge — console/data/_generate_ats.py — and the dual-read window are a scheduled Pillar follow-up.)

Open question — does an agent get a node?

Several Cairn FKs (attestor_id, attested_by) are typed fk(person.id), which collapses the AI-agent and human attestor cases. Whether agents become a sibling node type that shares the identity/consent layers with person but diverges on the time layer is the question Post 05 §X opens. It carries an open question badge and is escalated to the Chairman; until it resolves, treat attestor_id as person-or-agent, not person-only.
